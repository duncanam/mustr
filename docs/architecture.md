# Behavior, protocol, and safety

## One hub per space

Each Rust process owns one herdr space's socket, SQLite state, watcher jobs, scheduler, and optional Ratatui dashboard. Launch `mustr` in a tab of each space you want to coordinate. A same-space lock rejects duplicate instances; different spaces run independently, including their logs, restart recovery, and shutdown. Configuration and editable roles remain shared. There is no hub model or central shared conversation.

herdr supplies topology, not agent reasoning. mustr uses only `pane.current` and `workspace.list`: no terminal scraping, simulated user input, launching participants, or killing participants. Live pane identity takes precedence over inherited workspace environment variables. Socket identity includes filesystem instance information and the exact space ID, so neither another space nor a replacement herdr server can inherit stale coordination accidentally.

Each explicitly joined agent keeps its ordinary history, policies, selected model, and tools. Pi has a host-integrated extension; Claude Code has an explicit-wait MCP adapter with [more limited lifecycle guarantees](claude-code.md). A thin adapter provides current scoped state and addressed messages. The hub binds once to the launching pane's live herdr space, not an inherited workspace environment value. There is no space picker, navigation, or fallback. Refreshes may update that space's label or report it unavailable; they never retarget the hub, even if the launching pane moves. The actor holds one automation configuration, reset plan, epoch, and reset preview rather than routing among spaces. Models receive only their space's roster/task summaries and their own incoming messages, not neighbors' transcripts.

## Participation and human control

The lifecycle and command details below describe the Pi extension unless stated otherwise. Claude uses `mustr_join`/`mustr_wait`/`mustr_ack` and does not support automatic wake, settled-report enforcement, or fresh-session reset; see [Claude Code](claude-code.md).

Select a role with `/role NAME [PARTICIPANT-NAME]`. Role selection may precede hub startup: the adapter waits and reconnects with bounded backoff, without invoking a model. Connectivity, role selection, current activity, and task completion are separate facts. The dashboard's participant list counts and displays only connected agents (including paused ones). Offline identities remain stored for task/message name resolution and reconciliation; disconnecting does not erase unfinished tasks. A reconnect makes the participant visible again. Orderly leave or observed transport closure updates presence immediately; a missed heartbeat expires the presence lease after the 15-second stale threshold on a scheduler tick. Existing task notes distinguish lease expiry from transport closure, and both say execution may have continued rather than claiming a worker or external job stopped.

Assignments and automated prompts wait until Pi is settled. Live peer comments may enter an existing run at Pi's safe boundary, including a run started by the user. Ordinary user-started work is **working**, not paused. Pi-visible queued messages, editor drafts, dialogs, and explicit coordination pauses gate delivery. Informational messages are inserted without triggering a turn. Actionable messages trigger or steer an ordinary Pi turn through the extension API.

- `/mustr pause` is an explicit hold on incoming Mustr delivery; only `/mustr resume` or leaving releases it. Human and extension user starts do not implicitly resume it, and ordinary Pi tools remain available during the pause.
- Pi's public `input` hook is not correlated with an accepted user message. mustr does not infer or count input batches, match text/origin to `message_start`, or create a persistent delivery hold for handled/rejected preflight input. Native Pi pending-message/editor state still gates delivery when visible.
- Escape/abort and provider errors/retries are owned by Pi. mustr creates no persistent interruption or final-error hold and does not run its own retry loop. A native retry temporarily gates autonomous Mustr delivery until `agent_settled`, regardless of the final outcome; this gate does not block ordinary Pi tools.
- `mustr_pause` is for a genuine decision requiring the human, not ordinary task blockers, external waits or completion. Its coordination pause lasts until `/mustr resume` or leave, never an input event. Use `blocked`/`waiting` task reports for ordinary coordination so the requester can guide without a human resume command.
- `/mustr leave` ends participation and disables mustr tools in that session.
- Session replacement, reload, fork/tree navigation, or a detected move to another herdr space ends participation. Rejoin explicitly after reconciliation. Even a subsequently cancelled navigation attempt may require rejoining.
- Turning a mode off cancels **pending** prompts of that kind. A prompt already offered to Pi or work already started cannot be recalled reliably.

Neither cancellation, leaving, losing a connection, nor closing the hub proves a remote tool/job stopped. Existing project policies continue to govern all work.

## Addressed work and ownership

Model-facing tools are `mustr_roster`, `mustr_send`, `mustr_assign`, `mustr_report`, `mustr_guide`, `mustr_accept`, `mustr_cancel`, and `mustr_pause`. Communication tools must be called alone, not alongside sibling tool calls. In Pi they are model-only, not exposed through nested tool orchestration. Claude exposes them as ordinary MCP tools and adds explicit join/wait/ack/leave controls; it cannot enforce Claude's ordinary tool lifecycle.

A request message asks a question or requests attention; it does **not** assign ownership. An assignment records one requester, one owner, a title, scope, revision, and persistent FIFO sequence. An owner has at most one unfinished, non-Queued holder. Additional work may be assigned to a reachable, unpaused idle or working participant and waits in per-owner FIFO order across requesters. Queued work has no runnable assignment message and is not permission to start; the hub dispatches only when the owner is Idle, has no holder, is not retired or the TODO driver, and the space is not reset-frozen. Promotion occurs after assignment and at tick end; message-capacity pressure leaves the task queued.

```text
queued (bookkeeping only; no envelope)
  → eligible promotion → assigned → receipt → active → done report → review → requester accepts
                                                   ↘ blocked / waiting / paused → explicit guidance
```

The slot remains held through Assigned, Active, Blocked, Waiting, Review, and Paused. Only Accepted or Cancelled releases it; a later tick may then promote the next queued task. A requester may cancel its queued work without sending an owner message. A done report is not acceptance. Only the owner reports on its dispatched task; only the requester may Guide or Accept. A current admitted manager may cancel another requester's queued/current work only for explicit user-directed redirection. `mustr_cancel` cancels one task; `mustr_cancel_owner_tasks` requires an explicit `queued_only` or `all_unfinished` scope and a matching per-owner guard from the current roster. Guards cover the full selected task IDs/revisions/states, not only the bounded task rows, and stale guards fail before mutation. Bulk cancellation queues one aggregated nonwaking Info per other requester and a nonwaking owner Info only for a current holder; it returns affected IDs and says notices are queued, not delivered. Guidance increments the revision; stale revisions fail and guidance does not release the holder. Cancellation closes hub bookkeeping only; it never stops an external process or job. A Done report queues a waking notification to its requester independently of all automation modes; receipt does not prove that the requester performed the review.

The adapter stages `blocked`, `waiting`, and `done` reports and returns `terminate: true` to suppress automatic tool-call follow-up; queued or boundary continuations can still occur in the same native Pi run. While the report is provisional, productive tool calls in that run are fenced and same-task/revision work claims are rejected. `agent_before_settle` is only a candidate boundary: publication readiness is granted only at final non-aborted settlement when the latest candidate outcome is completed. A failed or aborted reporting run discards its provisional report. Only an explicit typed rejection before hub execution can retain an already-settled report for revalidation, including across unrelated later host failures or aborts. The provisional fence releases at actual settlement; a published terminal report fences that exact task revision from further work claims, but does not globally ban tools or ordinary work on later Pi turns. Only valid requester guidance/new authorized revision reopens the task; human or extension starts do not clear task/report scope. A validated waking child result or taskless manager checkpoint may set a separate, task-scoped coordination status without acting as guidance for the reported assignment. Human-directed reports may publish while Mustr delivery is paused. `status` is observational; `progress` explicitly resets the TODO no-progress nudge budget but still requires evidence and independent review.

## Three independent modes

Manager check-ins default on for a fresh space, waiting for an available manager. The saved check-in choice survives recovery, including an explicit off setting; existing off settings are not upgraded into consent. TODO and PR modes start off after startup/recovery. A reset disables all modes. Toggle them in this instance's dashboard with `t`, `c`, or `p`, or from Pi with `/mustr todo on|off`, `/mustr checkin on|off`, and `/mustr pr on|off`.

### TODO and unfinished-task continuation

Without an attached file, TODO mode nudges an idle owner only for an active assignment after the configured grace period. It does not resume blocked, waiting, review, paused, or disconnected work. Pending requests coalesce, and repeated nudges without progress pause the task for reconciliation.

`/mustr-todo [path/to/TODO.md]` attaches one explicit file and driver to the space, initially disabled. Nested Markdown checkboxes count; fenced examples do not. The hub reads but never edits the file. A reminder tells the driver to read the complete plan and independently verify criteria before checking boxes.

The driver is not nudged while it owns **or has delegated** unfinished tasks, preventing a second competing continuation. Unreadable/completed files and repeated cycles without checkbox progress disable the file cycle. New attachments replace the previous driver/file and cancel undelivered TODO prompts.

### Periodic check-ins

A selected role can declare root-only `manager = true`. The hub validates this from its own role files and admits at most one connected manager in the space. A paused manager retains the slot; leaving or disconnecting frees it for an explicitly joined manager role. There is no automatic election, role-name priority or fallback to an implementor. Manager metadata selects the checkpoint recipient and enables narrowly scoped cancellation for explicit user-directed redirection; it never grants Guide/Accept authority or general task ownership.

The manager watchdog replaces per-worker check-ins. The first verified manager join (or explicit enable) makes a checkpoint due at the next eligible tick; after enqueueing one, the next deadline is the configured interval later. Each checkpoint requests one bounded coordination pass over the existing goal: review results, resolve blockers within authority, check waiting conditions and continue already-authorized work. A checkpoint is a fresh hub-created, waking `checkin` with no task ID/revision, not replay of an old task notification. It can run with zero tasks or tasks in Review/Blocked/Waiting/Paused, because the hub cannot infer the manager's goal from task count. A truncated roster must not be treated as exhaustive. Per-member `task_queue` summaries give the current holder, queued count/next item, and separate deterministic `queued_only` / `all_unfinished` cancellation guards computed over the full selected task set; queued task rows carry FIFO positions.

Reminders coalesce and wait for an idle, unpaused manager. Busy, paused or missing managers are not replaced or forcibly resumed. Check-ins neither consume a task's TODO nudge budget nor change task state; the manager must explicitly inspect results, Guide/Accept only tasks it requested, and cancel another requester's work only when the user directs redirection. Periodic checks continue until mode off, including while the manager is legitimately monitoring a long external wait. This is bounded-rate scheduling, not an internal model polling loop or a guarantee of useful model decisions. The dashboard shows manager identity/availability. Transport heartbeats alone do not invoke models or count as progress.

### PR watching

When no watch is attached, dashboard `p` discovers the current branch's PR from the receiving participant's advertised checkout. A sole eligible participant is selected automatically; with several, a picker asks who should receive feedback. Only connected, unpaused participants with checkout context are eligible; roles confer no priority. Cancelling the picker does nothing, and a disappearing or paused selection is rejected rather than silently replaced. The hub's own working directory is never a discovery fallback.

From a joined Pi, `/mustr pr on` uses that authenticated participant as the recipient when no watch exists. Enabling starts asynchronous discovery in the existing watcher job, without blocking the actor or client heartbeats. It resolves the Git root and branch, rejects detached HEAD, and calls `gh pr view` without a PR argument, using GitHub CLI's current-branch/upstream selection. The returned PR must be open, have the matching head branch, and use a canonical GitHub.com URL. Complete, identity-stable collection pins the URL and checkout root atomically. There is no model inference or search through other agents' histories. Discovery errors disable the watcher and show the reason. An unresolved watch retains its chosen driver and exact advertised checkout; retries require that same connected, unpaused participant and directory. Correct authentication or restore/rejoin the original checkout before enabling again. To change the binding deliberately, use an explicit `/mustr-pr URL` attachment from the intended recipient.

`/mustr-pr https://github.com/OWNER/REPO/pull/NUMBER` still attaches an explicit PR, checkout, and recipient, initially disabled. A resolved binding is reused when enabled, not rediscovered; an unresolved discovery watch retries only against its original bound driver and checkout. Neither path silently retargets to the caller or another participant. The hub runs bounded, read-only `git rev-parse`, `gh pr view`, and paginated `gh api .../pulls/.../comments` commands; it cannot commit, push, merge, comment, rerun CI, or change branches.

Observations cover conversation comments, review decisions, inline comments/replies, and failed check/status results. Fingerprints include edited content. Existing feedback is baselined on first observation; existing failed checks are actionable. Checks are tied to the remote head. The local branch must match the PR branch, and both local and remote identity are rechecked during collection.

A baseline advances only with a complete observation and, for actionable deltas, confirmed message receipt. Disabling/re-enabling the same watch preserves its baseline. Replacing an in-flight offered PR notification is rejected until receipt/disconnection resolves it. New watcher generations discard late results. Old pending feedback is refreshed before delivery rather than acted on after a long pause.

Closure/merge disables watching. A failed or inconsistent poll, including branch changes or authentication errors, pauses the watcher and cancels pending feedback; inspect the dashboard error and explicitly re-enable or reattach it. GitHub content is untrusted evidence. Notifications are bounded previews, not a replacement for reading full linked feedback. `gh pr view` governs availability of conversation/review data; mustr does not claim a complete archival export of arbitrary-sized PRs.

## Durability and wire protocol

Protocol v1 is UTF-8 newline-delimited JSON over a same-user Unix socket. The v3 state payload stores a defaulted `seq` on tasks and a defaulted `next_seq`; recovery raises the counter beyond every stored sequence, while exhaustion fails new assignments closed. The schema version is not bumped. Older v3 payloads without these fields remain readable, but older binaries do not recognize `queued` and therefore fail closed rather than safely running a new queued state. Do not downgrade while queued work may be present. Each connection first sends `join` with protocol version, session ID, role/name, pane/space IDs, and optional absolute checkout directory (`cwd`). Updated Pi and Claude adapters advertise their own working directory; older clients without it remain usable but cannot be selected for automatic PR discovery. This live checkout context is not included in peer roster JSON or persisted as participant metadata; an explicitly enabled watch retains its own checkout binding. The server checks the live pane, its match to this hub's immutable space, and the supported agent designation (`pi` or `claude`), and resolves the requested role graph before admitting the participant, including reconnect and fresh-session joins. Manager status comes from that validated root role, not an extra client-supplied Join field; duplicate manager admission is rejected. The actor independently rejects foreign-space joins and control events; stored records must also match its bound space. The designation is bound to the connection; replacing the harness requires explicit rejoining. Invalid roles fail before participant/reset state changes; unrelated valid role graphs remain usable. Subsequent operations bind to that sender; recipients and task IDs cannot cross spaces.

```json
{"id":"unique-request-id","op":"send","to":"recipient-session-id","text":"Please review task X","wake":true}
```

Responses carry the request ID, `ok`, and either `result` or `error`, with an optional `error_code` for an explicitly classified rejection. `sync` reports activity and may offer one inbox message; `ack` confirms its receipt. The Rust `Command` enum in `src/protocol.rs` is the complete versioned command schema. Unknown command fields are rejected.

SQLite is the single writer's transaction boundary. Each operation applies to a cloned state. Durable mutations and message offers persist atomically before replies; presence heartbeats remain ephemeral and no-op ticks do not rewrite the database. Failed transitions cannot partially commit. Corrupt or incompatible state fails closed, rather than resetting silently.

Addressed peer requests, information, and status/blocked/done reports use push-driven receipt, without waiting for the whole run to end or a polling tick. After explicit `subscribe`, Rust sends a content-free `{"event":"inbox_ready"}` socket hint when the bound recipient has eligible queued work. Hints are recipient-scoped and coalesced; unsubscribed clients receive no extra frames. Readiness uses the complete queue, not the dashboard's 200-message preview. The adapter wakes its serialized pump immediately; the normal validated `sync` transaction still owns offering. One-second polling remains a fallback and heartbeat, not the primary delivery mechanism. Local process/socket scheduling and Pi's safe insertion boundary still impose latency; this is not a real-time execution guarantee. Actionable messages use Pi's steering queue at its next safe boundary; informational messages are appended after the current turn's tool results without forcing a new model turn. This is not cancellation of a running tool. Assignments, task resumptions, and automated TODO/check-in/PR prompts remain idle-only; eligible live comments can bypass those queued messages. Pi-visible queued messages, editor drafts, dialogs, explicit pauses, identity/reset fences, transient native retry, and staged terminal reports gate delivery; an uncorrelated `input` hook alone does not. Already-inserted/queued messages are not recalled by a later pause.

The adapter keeps heartbeating while Pi waits to insert a live message. Rust enforces at most one offered message per recipient, even if a client repeatedly requests another. `sync` supplies the Rust-selected `insertion_policy` (`live` or `idle_only`); the adapter rechecks Pi-visible pending-message, editor, activity, dialog, and pause state before insertion. If that host-visible state races with the offer, `defer` returns it without disconnecting, but only before any insertion attempt. Rust discards deferred prompts whose task/revision or automation mode has been superseded. Once insertion is attempted, deferral/replay is forbidden. A long model/tool call is not treated as an insertion timeout; an initially idle offer that becomes working loses its short deadline. Idle delivery retains its bounded confirmation timeout.

Delivery states are **pending**, **offered**, **received**, **uncertain**, and **cancelled**. The adapter records an **attempt marker**, not a receipt, before injecting a message. Only a matching `custom_message` entry on its current session branch proves insertion and permits acknowledgement. Pi 1.2's informational (`triggerTurn:false`) path persists messages and emits public SDK events without calling extension `message_end`; waiting for that extension callback caused false timeouts/disconnects. Polling the actual entry covers both informational and actionable delivery without forcing a model turn. A marker alone prevents reinjection but never authorizes acknowledgement. Receipt is neither execution nor completion; there is no exactly-once model-execution guarantee.

Rust validates persisted/wire states before constructing private, non-Clone `Pending`/`Offered` transition capabilities. Consuming an offer produces receipt effects that can activate the matching assignment revision and advance a PR baseline once. Only offered messages can be deferred; uncertain/received/cancelled messages cannot. These are compile-time constraints inside the delivery module, not a claim that Rust can prove an external Pi insertion or eliminate runtime validation at JSON/SQLite boundaries. The v1 join reply advertises `delivery_policy: 1` and `inbox_notifications: 1`; the updated adapter requires both, so update/restart the hub before rejoining with the updated adapter. Incoming hints and lifecycle events coalesce into one pump; they never overlap a running pump or bypass host-visible delivery gates.

A temporary herdr lookup failure is not proof of identity change. The hub validates the authenticated pane, space, and harness on every request; an `identity_unavailable` response means that specific request was rejected **before** actor execution, so it applied no heartbeat/activity, task mutation, inbox offer, or ACK. On a healthy connected Pi pump, the adapter reuses its established pinned identity and sends the ordinary sync without launching `mustr context` every tick. Before ordinary hub dispatch—including model/UI operations and inbox follow-ups—it cheaply compares the verified snapshot of the actual `HERDR_ENV`, `HERDR_SOCKET_PATH`, and `HERDR_PANE_ID` inputs consumed by `mustr context`; any mismatch invalidates that snapshot and blocks old-pin requests until discovery. The snapshot is refreshed only after context succeeds and those inputs are unchanged across the child call. A same-identity discovery resumes on the existing connection; changed/invalid identity stops locally without an unverified Leave or auto-rebind. If any hub request returns typed `identity_unavailable`, Pi retains the socket but enters the same identity hold: it sends no further heartbeat, report, ACK, mode/configuration request, or inbox action until a fresh context discovery succeeds and matches the pinned identity. The hold also invalidates results from an older in-flight sync before they can authorize stale roster/reset/task-scope data or follow-up dispatch; already-issued requests cannot be recalled. If a successful sync already created a server-side offer, Pi keeps local ownership of that never-inserted offer through the rest of the pump—including awaited ACK/report work—until `receive` transfers it to delivery/defer or common pump cleanup retains only the offer ID as a defer intent bound to the same client/generation and pinned identity. Thus an identity gate after a successful report cannot strand the offered ID. Pi sends the existing `defer` only after successful same-identity validation; socket closure or changed identity clears the intent, while insertion evidence or an incompatible intent closes the connection for reconciliation. Initial joins, rejoin, identity recovery, and existing reset/replacement checkpoints still discover and compare context. For `mustr context` only, the CLI maps the existing typed `HerdrUnavailable` to reserved exit status `75`, with concise stderr and no JSON stdout or color-eyre chain; success JSON is unchanged. Pi recognizes only numeric child exit `75` from that command as transient and uses the existing bounded backoff; expected local/server identity retries remain visible in persistent status rather than warning popups, and same-identity recovery clears that status. Typed identity rejection from UI mode/configuration commands enters the same hold; the rejected action is not replayed. Explicit leave and role-switch cleanup detach locally without a hub Leave while identity is unverified, and any new role must pass context validation before admission. A successful pump clears the persistent retry status, so a later outage is distinct. Configuration/environment/socket metadata and permission errors, malformed protocol/topology/output, instance replacement, generic exits, spawn failures, parent timeouts and signals are visible nontransient failures that stop participation and require explicit role selection; there is no automatic rejoin. No cached permission authorizes action while identity is unverified. Actual pane/space/harness changes and server replacement remain fatal; the server socket incarnation is checked both before and after lookup. The herdr request deadline (three seconds), Pi child watchdog (six seconds), identity retry backoff, and presence policy are unchanged; outages exceeding the existing 15-second stale threshold can still expire presence and require reconciliation.

A typed `connection_retired` response is narrower: the hub returns it only when a stored binding has been revoked, superseded by a newer incarnation, or invalidated by current member/reset state, and it does so before actor execution or request-cache mutation. Pi closes that offending client without Leave or automatic rejoin, disables Mustr participation, and requires an explicit `/role` after context validation and normal hub admission; it does not fabricate a fresh identity or resume paused tasks. Cleanup is guarded by the captured client and generation, so a delayed old response can close only its old client. During a reset/frozen/restore fence, retirement stops coordination but preserves the private reset hold and recovery evidence. Claude continues to require an explicit `mustr_join`. Connection retirement does not stop external work; reconcile it before rejoining.

Only that explicit non-execution reply allows Pi to retain and later submit a staged report, insertion-proven ACK or not-yet-inserted deferral on the same connection. User/extension starts do not clear a retained report or alter task scope. Abort before successful settlement discards that run's staged report; session/generation changes invalidate obsolete intent. Model-issued mutations are not automatically retried. Missing/uncertain acknowledgements never qualify for this exception.

A disconnect/restart marks pending/offered deliveries uncertain and pauses active/assigned work. Reconnection does not replay those messages. Notes distinguish an expired presence lease from an observed transport close or explicit leave, while warning in every case that execution may have continued. TODO continuation skips paused work, even with an idle, reconnected owner. A manager checkpoint may ask the requester to reconcile it but does not itself resume it. The dashboard shows the pause reason and requester responsible for recovery: inspect files, job status, and task notes, then have that requester explicitly guide or cancel. `/mustr resume` releases a participant's local pause; it does not resume a paused assignment. Do not blindly reassign uncertain work. A cancelled completion **notification** does not mean the task was cancelled: acceptance can supersede a queued done notification while leaving the task accepted. The adapter never retries a timed-out mutation automatically. Request deduplication retains the most recent 1024 mutations; it is not an indefinite replay guarantee.

## Prompt context and cache stability

Pi role instructions append to the host's structured system-prompt options without replacing its other sections. Live roster/task snapshots belong in explicit `mustr_roster` results and addressed messages, not a changing synthetic message appended on every model request. Heartbeats therefore do not rewrite model context or invoke models. Refresh the roster when coordinating; an earlier snapshot is not authoritative current state. Pi's roster identifies `self: { id, name, role }` so same-role participants can identify their own tasks without per-request identity injection. By default, model-facing roster content keeps every unfinished task summary complete—including queued tasks and their positions—and replaces Accepted/Cancelled entries with snapshot-local counts and up to three note-free samples in hub-returned order; the sample is not a global recency ranking. The hub prioritizes a caller-owned holder in the bounded task array and adds a compact holder/queue summary per member, so queued overflow cannot hide that holder from task permits. The `tasks_truncated` flag remains authoritative because the hub may omit summaries. Set `include_finished: true` to show every task summary returned in that sync, still subject to hub truncation. Tool details retain the full safe returned roster in either mode.

Ordinary tool continuations retain their existing message prefix. Joining, changing roles or tools, compaction, and other extensions can still change requests; provider cache eligibility and hits are not guaranteed by mustr. No-model tests verify request construction, not paid-provider cache behavior.

## Human-confirmed fresh start

The dashboard's `r` action previews a reset of its bound space; typing `RESET` after inspecting the dialog confirms it. This is a human-only Service operation, not a socket command or agent tool. It captures exact participants and history, revalidates the preview, freezes coordination and disables automation. Each supported connected Pi adapter must claim one private reset ticket, pass native idle, pending-message, editor, dialog, tool and identity checks, and create a genuinely new session. Readiness is limited to host-visible evidence; it cannot prove every hypothetical asynchronous input preflight has resolved. Fresh-session restore retains its deny-only human-input evidence. Only a validated fresh-session join confirms that participant; receipts and ordinary idleness are not completion evidence. Policies/tools and approved roles remain; old conversations are not copied.

After all participants confirm, the actor atomically clears that space's tasks/messages, retires old identities, detaches TODO/PR bindings and leaves automation off. Other spaces and user files remain unchanged. Disconnected agents' saved context is not remotely cleared; old Pi session files remain available. This is not secure erasure and never stops external jobs.

A veto, failed claim, disconnect or ambiguous replacement leaves durable incomplete progress and retained hub history, not a false success. Claim attempts are not automatically replayed. The separately confirmed **Abandon attempt** action retains history/bindings, invalidates tickets, marks unresolved delivery/work for reconciliation, and releases the freeze without restoring old Pi contexts. An already-issued replacement may still finish but its revoked receipt is rejected. Affected agents may need manual `/new` and `/role NAME`. See [Start fresh](start-fresh.md) for the exact scope and recovery steps.

Reset progress, private claims and retired identities persist across restart; watcher generations and connection epochs fence stale activity. Database version 3 stores the immutable space owner and singleton state; older binaries cannot safely read it. Per-space databases preserve history across restarts. Old shared multi-space history is not imported or modified. Reset control tokens are private transport data, excluded from roster/model context and public progress summaries.

## Trust, storage, and current limits

This is a cooperative **same-user** system, not authentication against hostile processes running as your UID. Private directories, socket permissions, instance checks, and live-pane checks limit accidental routing and other-user access; another same-user program can impersonate a participant. Roles do not sandbox filesystem/tool access.

SQLite stores participant identities, task descriptions/notes, addressed message text, delivery state, TODO paths, PR checkout paths and URLs, and feedback fingerprints. Pi stores delivered messages and receipt markers in its own session. Claude receives messages in MCP tool results and acknowledges them in a subsequent explicit `mustr_ack` call; the bridge keeps only an in-memory outstanding offer, not a durable Claude-session receipt. No private neighbor transcripts are read. State is not encrypted; protect the user account and backups.

Current bounds include 256 KiB frames, 6000-byte user message text, 256 remembered participants, 1000 tasks, 1000 retained messages, 1024 deduplication records, a 16 MiB state document, and a 1 MiB TODO file. Completed/cancelled messages can be pruned at capacity; unresolved deliveries are not silently dropped. Roster replies prioritize unfinished/owned tasks, return at most 64 task summaries, mark truncation, and bound note previews. Each queued row's `queue_position` is relative to all queued work for that owner, not just the truncated rows; member summaries expose total queued count and the next item. The dashboard displays the latest 200 messages. Tasks and Messages share a tabbed pane with independent scrolling; `f` changes the active work tab; this never changes the hub's space. The task total and accepted-completion count remain visible on both tabs (awaiting-review and cancelled tasks are not completed). Message bodies are 240-character previews with an explicit truncation marker; scrolling clamps to the wrapped content bounds.

The confirmed dashboard reset clears one space's history; it is not automatic garbage collection. If a state/storage limit prevents safe reset or persistence, reconcile outstanding work, stop the hub and intentionally archive that instance's per-space SQLite files before starting fresh. Do not remove a reset fence or downgrade the database to work around a blocked operation. Local Unix sockets only: no Windows support, cross-machine routing, distributed consensus, or unattended manufacture/production approval. herdr API compatibility was inspected against 0.9.5; Pi typechecking uses 1.2.0. End-to-end tests use fake topology/agents, not paid models. Claude MCP tests exercise protocol handshakes and mixed-harness coordination without claiming live-model or Claude-host lifecycle validation.
